## What this is

Show Shot — a Flutter desktop screenshot/annotation app for macOS, Windows and Linux (Flameshot/Lightshot-style: freeze the screen, pick an area/window/full display, annotate, copy or save). Lives in the menu bar/tray, responds to global hotkeys. See [README.md](README.md) for the full user-facing feature list and platform build steps — this file is for working *on* the code, not using the app.

**Cross-machine note:** this project gets worked on from multiple machines (macOS, Windows 11, Ubuntu 26.04 x64/arm64). This file is the shared source of truth for status/next-steps across those sessions — keep the "Current status" section below updated as work lands, so a Claude session opened on a different OS picks up where the last one left off instead of re-discovering it.

### Debug automation server (no mouse/keyboard needed)

Debug builds (`kDebugMode`) open a line-oriented TCP server on `127.0.0.1:47391` (`lib/debug/debug_server.dart`) that drives the whole capture → overlay → editor flow programmatically — essential when you can't simulate real clicks (no Accessibility permission on macOS, and Wayland blocks synthetic input entirely on Linux):

```bash
printf 'capture area\n' | nc 127.0.0.1 47391
printf 'select 100 100 600 400\nconfirm edit\n' | nc 127.0.0.1 47391
printf 'tool arrow\ndraw 50 50 300 200\ntext 100 300 hi\naction save\n' | nc 127.0.0.1 47391
```

Commands: `capture area|window|fullScreen`, `select x y w h`, `hover x y`, `windows` (lists detected windows), `confirm edit|copy|save|cancel`, `tool <name>`, `draw x1 y1 x2 y2 [...]`, `text x y <text>`, `color AARRGGBB`, `style <width> <opacity> [fill]`, `undo`, `action save|saveAs|copy|discard`, `setting ask|copyAfterSave|magnifier|jpg|language true|false|<value>`, `home`, `settings`, `hide`, `close`, `stage`, `quit`.

Hot-reload a running `flutter run` session from another shell with `kill -USR1 <pid>` (find the `dartvm ... flutter_tools.snapshot` process), rather than restarting — the debug server survives reloads.

## Architecture

**One OS window, three roles.** There's a single native window that switches between *home* (Material UI), *overlay* (borderless, frozen-screen selection) and *editor* (annotation canvas) roles — `lib/flow/capture_flow.dart`'s `CaptureFlow` orchestrates the transitions (`window_manager` for resize/show/hide, `Navigator.pushNamedAndRemoveUntil` for the route swap). Routes: `/`, `/settings`, `/overlay`, `/editor`, and a `/blank` route used briefly during transitions specifically to drop widget references to a `ui.Image` *before* it gets disposed (skipping that step throws "Cannot clone a disposed image").

**Native bridge, one per platform, same Dart-side contract.** `lib/services/native_bridge.dart` talks to a `shoshot/native` method channel implemented independently per platform — there is no shared native code:

| Platform | File | Capture | Window list | Overlay |
| --- | --- | --- | --- | --- |
| macOS | `macos/Runner/ShoShotNative.swift` | ScreenCaptureKit (`SCScreenshotManager`, macOS 14+) → `CGDisplayCreateImage` fallback | `CGWindowListCopyWindowInfo` | borderless `NSWindow` at `.screenSaver` level |
| Windows | `windows/runner/shoshot_native.cpp` | GDI `BitBlt` per monitor (per-monitor DPI) | `EnumWindows` + DWM (skips cloaked/tool windows) | `WS_POPUP` + `WS_EX_TOPMOST` sized to the monitor rect |
| Linux | `linux/runner/shoshot_native.cc` | X11 `XGetImage`; Wayland has **no native capture path yet** (see below) | `_NET_CLIENT_LIST_STACKING`, X11 only | `gtk_window_fullscreen_on_monitor` |

`DisplayInfo` (`lib/models/display_info.dart`) normalizes the coordinate systems: macOS reports points (`globalIsPhysical: false`), Windows/Linux report physical pixels (`globalIsPhysical: true`) — `NativeBridge.getDisplays()` reads `platformInfo()` once and converts accordingly. Never assume one scale everywhere.

**Capture flow:** `CaptureService.captureUnderCursor()` freezes the display under the *cursor* (not the focused display) into a `CaptureSession` (`lib/models/capture_session.dart`), which holds the raw `ui.Image` plus the window list already translated into that display's local logical coordinates (`CaptureSession._localizeWindows`). The overlay (`lib/ui/overlay/overlay_screen.dart`) never touches native APIs directly — it only reads the frozen `CaptureSession`.

**Overlay hit-testing gotcha (already fixed once, don't reintroduce):** the overlay's full-screen `Listener` (drag-to-select) must **not** be an ancestor of the floating action bar / hint / magnifier. A `Listener` receives every raw pointer event under its subtree regardless of which descendant widget consumed it — so if the action bar is a child, clicking a toolbar button also re-triggers `_onDown` on the Listener and looks like "the selection just expanded". They must be siblings inside the same `Stack` so the Stack's hit-test short-circuits at the topmost hit child. See the `build()` method's structure/comment in `overlay_screen.dart`.

**Window-picker mode vs. area mode** (`CaptureMode.window` vs `.area`) share the same `OverlayScreen`, differentiated by mode checks in the pointer handlers: window mode never builds a free-drag rectangle (any mouse-down+up resolves to whichever window is under the cursor at release, regardless of incidental drag distance — real clicks always have a few pixels of jitter, so gating on "did it move" breaks window-picking). Window mode also swaps the system cursor for a custom camera-icon badge and drops the magnifier/crosshair (`_isWindowPickPhase` in `overlay_screen.dart`), and the hovered window is "spotlighted" (undimmed, like a live selection preview) in `overlay_painter.dart`.

**Editor** (`lib/ui/editor/`): `EditorController` (a `ChangeNotifier`, not a widget) owns the annotation list, undo/redo stack, active tool/style and viewport transform; `EditorCanvasPainter` just renders `controller.paintable`. Annotations (`lib/models/annotation.dart`) are a small sealed-ish hierarchy (`ShapeAnnotation`, `StrokeAnnotation`, `TextAnnotation`, `NumberAnnotation`) each implementing `paint`/`hitTest`/`translated`/`withHandle` — add new tools here, not by branching on `ToolType` elsewhere. Coordinates throughout the editor are *image pixel* space, not logical/window space (`EditorController.pixelRatio` converts UI slider values like stroke width to pixels).

**Services are plain classes wired by hand** in `lib/main.dart` and exposed via `AppScope` (a thin `InheritedWidget`, `lib/core/app_scope.dart`) — there's no DI framework. `SettingsService` and `CaptureFlow` are `ChangeNotifier`s persisted/observed the normal Flutter way; widgets read them via `AppScope.of(context)` + `ListenableBuilder`.

**i18n gotcha:** `Strings.of(context)` (`lib/core/strings.dart`) returns a `const` PT/EN instance — cheap, but that means a screen that captures it *outside* a `ListenableBuilder` reactive to `services.settings` will show stale text after an in-page language change (this happened once in `SettingsScreen` — fixed by moving the whole screen inside one `ListenableBuilder`). Any screen with a live language-dependent control needs the same pattern.

**Theming (2026-09-20):** the app now follows the OS light/dark mode (`ThemeMode.system` — Flutter's engine already detects this on every desktop platform, no native code needed) and the OS accent color (native-only signal, no Flutter API for it). Verified end-to-end on macOS: toggled System Settings between light/dark and cycled accent colors (including a dramatic Pink) while the app was running — both update live with zero restart. Architecture:

- `lib/core/theme.dart`: `AppPalette` (a `ThemeExtension`) holds the OS-driven tokens (bg/surface/border/text/accent-gradient) for **widget chrome** (Home, Settings, dialogs, editor/overlay toolbars) — read via `context.palette` (`AppPaletteContext` extension). `AppColors` keeps only what must stay fixed regardless of theme: the annotation color swatches, `danger`/`success`/`warning`, and `violet`/`cyan` — the latter two used *only* by `CustomPainter`-drawn canvas chrome (overlay selection border, spotlight, camera-cursor badge, editor selection handles), which is painted directly over arbitrary screenshot content and needs guaranteed contrast a pastel OS accent couldn't promise. Don't blur this line when adding UI: Material widgets → `context.palette`; `Canvas`/`CustomPainter` code → `AppColors` fixed accents.
  - **Don't trust `ColorScheme.fromSeed(seedColor: accent).primary` to look like `accent`.** Material 3 remaps the seed onto its own tonal palette — in dark mode this produced a pale, desaturated periwinkle (`#ABC7FC`) from a real macOS Blue seed (`#0A84FF`), which reads as visibly "wrong" next to the rest of the OS (found by literally sampling the rendered pixel of a themed `Switch`, not by eyeballing a screenshot). `AppTheme.build()` works around this by generating the tonal scheme normally, then overriding `primary`/`onPrimary`/`primaryContainer`/`secondary` back to the literal accent color — keep doing that for any new accent-driven token; don't reach for `scheme.primary` directly expecting it to match.
- `lib/models/system_theme.dart` + `lib/services/system_theme_service.dart` + `NativeBridge.getSystemAccent()`/`onSystemAccentChanged`: reads the OS accent once at startup (awaited before `runApp`, so there's no fallback-color flash) and stays in sync via a native→Dart push (`systemAccentChanged` on the `shoshot/native` channel).
- Per platform: macOS reads `NSColor.controlAccentColor`, observed live via `DistributedNotificationCenter` (`AppleColorPreferencesChangedNotification`). Windows reads `HKCU\Software\Microsoft\Windows\DWM\AccentColor` (ABGR DWORD), refreshed on `WM_SETTINGCHANGE`/`WM_DWMCOLORIZATIONCOLORCHANGED`. Linux reads `org.freedesktop.portal.Settings` (`org.freedesktop.appearance`/`accent-color`) over D-Bus and subscribes to its `SettingChanged` signal — this is a recent portal addition, so expect it to be unimplemented on some setups; the code already falls back to the fixed violet default when the call fails, which is the expected/silent path there, not a bug.
- Icons live in `artwork/` (SVG + PNG sources, both light/dark variants for the app icon and tray icon) — regenerate `assets/branding/`, `assets/tray/`, `windows/runner/resources/app_icon.ico` from there if the mark changes. The macOS tray icon stays a single `isIconTemplate` asset (OS auto-recolors it); Windows/Linux tray icons don't get OS recoloring, so `TrayService` picks the light/dark-glyph asset itself from `PlatformDispatcher.platformBrightness`.
- **macOS app icon is now an Icon Composer `.icon` bundle** (`macos/Runner/ShowShot.icon`, sourced from `artwork/ShowShot.icon` — regenerate/re-copy from there if the icon changes), not a classic `AppIcon.appiconset` (deleted). Wiring one into this Flutter-template project (classic `objectVersion = 54` pbxproj, not the newer synchronized-groups format) took real trial and error — don't rediscover it:
  - It must be added as a **loose `PBXFileReference`** in the target's Resources build phase (`macos/Runner.xcodeproj/project.pbxproj`), with `lastKnownFileType = com.apple.iconcomposer.icon;` — that exact string is the real system UTI (confirmed via `mdls -name kMDItemContentType` on any `.icon` file), not an Xcode-internal alias like `folder.assetcatalog`. Get this type wrong (e.g. generic `folder`) and the build "succeeds" but just **raw-copies the `.icon` folder into `Contents/Resources/`** instead of compiling it — no error, just a silently wrong result (the app then shows the generic blank-page placeholder icon).
  - It must **not** live inside `Assets.xcassets` in this project — that seemed plausible (works that way in newer, natively-created Xcode 26+ projects using `PBXFileSystemSynchronizedRootGroup`) but silently failed here too (also no icon, also no error) — this template's classic pbxproj apparently needs the explicit loose reference instead.
  - `ASSETCATALOG_COMPILER_APPICON_NAME` (all 3 build configs) must equal the icon's name without extension (`ShowShot`, not `"Show Shot"` — a leftover mismatch from an earlier bulk rename pass, worth double-checking any project-wide find/replace against pbxproj build settings, not just source files).
  - Success looks like: `assetcatalog_output/thinned/ShowShot.icns` appears in the build log, `Info.plist` gets real `CFBundleIconFile`/`CFBundleIconName` values, and nothing named `ShowShot.icon` ends up inside the built `.app`'s `Contents/Resources/`. Verify visually too (`osascript … reveal` + `screencapture`, or just look in Finder) — a wrong-but-non-erroring config is easy to ship unnoticed otherwise.
  - The resulting `actool` compile also emits a flattened `.icns` automatically, so no separate pre-Tahoe fallback icon is needed.

**Linux/Wayland has no native capture, window list, or global hotkeys at all today** — `CaptureService` falls back to shelling out to `gnome-screenshot`/`spectacle`/`grim`/`scrot` (whichever is on `$PATH`) for a screenshot and returns an empty window list; `hotkey_manager`'s X11 backend (`keybinder-3.0`) doesn't work under Wayland either. This is a real gap, not a nice-to-have: the primary Linux target is Ubuntu 26.04 (GNOME/Wayland by default, both x64 and arm64), so this needs proper portal-based support, not just a CLI fallback:

- **Screenshot:** use the `org.freedesktop.portal.Screenshot` D-Bus interface (via `xdg-desktop-portal` + `xdg-desktop-portal-gnome` on Ubuntu) instead of shelling out. It shows a native permission/picker dialog per call (no persistent grant for plain screenshots, unlike ScreenCast) — factor that into the UX (can't freeze-then-ask; may need to ask first, or accept the portal's own picker instead of our custom overlay for the initial capture).
- **Window enumeration:** Wayland deliberately has no global "list all windows" API for security reasons — there is no drop-in replacement for `_NET_CLIENT_LIST_STACKING`. The realistic path is to lean on the portal's own window/screen picker UI for "Window" mode under Wayland (i.e., a different, portal-driven UX from the X11 custom-overlay picker, not a like-for-like replacement), or use the ScreenCast portal's source picker if `capture window` needs to keep working.
- **Global hotkeys:** the modern answer is the `org.freedesktop.portal.GlobalShortcuts` portal (needs a recent `xdg-desktop-portal`; verify what Ubuntu 26.04 ships). GNOME also has its own custom-keybinding path via `gsettings`/`org.gnome.settings-daemon` as a fallback if the portal isn't available.
- Detect Wayland vs X11 at runtime the same way `shoshot_native.cc` already does (`GDK_IS_WAYLAND_DISPLAY`) and branch the whole capture/hotkey/window strategy on it — X11 (still selectable at login on Ubuntu) should keep using the existing, working native path.
- This needs to be built and iterated *on* an actual Ubuntu Wayland session — portal APIs are version- and compositor-sensitive enough that guessing from outside is unreliable.

**Branding:** display name is "Show Shot" (with a space); bundle/application id `com.rafaelwms.showshot`; site `showshot.rafaelwms.com`. The Dart package name (`shoshot`), repo folder (`app-shoshot`), method channel (`shoshot/native`), and class names (`ShoShotNative`, `ShoShotApp`) were deliberately left as internal technical identifiers — a full rename would touch 30+ files across 3 native build systems; flag it to the user before doing that, don't do it silently.

**Fixed 2026-09-20/21: second capture from Home "did nothing" on macOS — two real bugs stacked, plus one wrong fix along the way.** User report: clicking a capture card on the Home window worked once; after returning from the overlay (whether by completing or cancelling with Esc), every further click on Home did nothing at all — but closing the window and reopening it (e.g. from the tray) always unstuck it.

First attempt was wrong and worth recording so it isn't retried: since the debug server's `capture area` (calls `CaptureFlow.start()` directly) reproduced a clean overlay every time, and the only structural difference between "via Home" and "via tray" is whether the click has to land on the app's own window, the working theory was AppKit's standard first-click-suppression on a non-key window. Fixed `MainFlutterWindow.swift` with a `sendEvent(_:)` override that calls `makeKey()` before forwarding `.leftMouseDown` — this compiled, ran, and *looked* plausible, but the user re-tested and the bug was identical. That fix was reverted (see git history) once the real cause was found, rather than leaving unproven speculative code in place.

Since the debug server can't drive real clicks, diagnosis from here on used temporary `debugPrint` logging plus having the user reproduce the bug physically while the app ran under `nohup ... > log 2>&1` — the log doesn't need a live `flutter run` session, just redirected stdout, and can be read after the fact without touching the keyboard/mouse. This is the general pattern for this class of bug in this project: the debug server proves the *state machine* logic is correct but can never catch a UI-layer bug, since it doesn't go through real gestures or listener wiring at all.

**Bug 1 (real, but not sufficient on its own): `completeOverlay()`'s `finally` never called `notifyListeners()`.** First log showed `_CaptureCard` rebuilding fine and `MouseRegion.onEnter` firing on every hover (window/hit-testing/mouse-tracking were never broken); the first tap correctly flips `enabled` to `false`; `completeOverlay()` runs its full sequence including `showHome()` (which does its own `notifyListeners()` while `_busy` is still `true`, so Home correctly rebuilds disabled at that point) — but then `completeOverlay()`'s own `finally { _busy = false; }` ran *after* that last notification without calling `notifyListeners()` itself, so nothing told the `ListenableBuilder` that `flow.busy` had gone back to `false`. Fixed by adding `notifyListeners();` right after `_busy = false;` in both `finally` blocks (`start()` and `completeOverlay()`) in `capture_flow.dart`. **This fix was necessary but the bug persisted anyway** — the user re-tested and it was unchanged, which meant there was a second, independent bug.

**Bug 2 (the actual blocker): `const left = _CaptureColumn(); const right = _RecentColumn();` inside the `LayoutBuilder` in `home_screen.dart`.** Re-instrumented with logging directly in `_CaptureColumn.build()` and traced it to Flutter's own `Element.updateChild` optimization: when a parent rebuilds and produces a widget that is `identical()` to the one already mounted in that slot — which `const SomeWidget()` with no constructor arguments always is, since Dart canonicalizes it to a single shared instance — Flutter skips calling `build()` on it entirely (`if (child.widget == newWidget) { ...; return child; }`, no `rebuild()`). `_CaptureColumn`/`_RecentColumn` read mutable state (`AppScope.of(context).flow` etc.) in their own `build()`, so marking their *instantiation site* `const` is exactly the documented Flutter anti-pattern ("don't const a widget that depends on something that can change"). Concretely: a *fresh* route push (e.g. `showHome()` called while `_busy` was still `true`, mid-`completeOverlay()`) mounts a brand-new `_CaptureColumn` element and correctly bakes in `enabled: false` at that moment — but any *later* `notifyListeners()` on the same already-mounted Home (including the Bug 1 fix's own call) tries to update that existing element with the identical `const` instance, and Flutter silently no-ops it. The capture cards were then frozen at whatever `enabled` value happened to be true at last mount, forever, until the next full route push (closing and reopening the window forces exactly that, which is why it "fixed" it). Fixed by dropping `const` from those two instantiations (and the `const Expanded(..., child: right)` that depended on `right` being const) in `home_screen.dart` — plain `final left = _CaptureColumn();` etc.

Lesson for next time this shape of bug shows up (a `ListenableBuilder`/`AnimatedBuilder` that's provably notified but the UI still doesn't reflect new state): check for a `const` widget instantiation *inside* the rebuilding scope that reads inherited/provider state in its own `build()` — `notifyListeners()` firing correctly is necessary but not sufficient if something downstream is `const`-cached. And more generally: a bug that "goes away if you close and reopen the window" is a strong hint that a *fresh mount* is doing something a same-instance *update* isn't — diff those two code paths, don't just add more notifications.

**Fixed 2026-09-20: macOS underlined every word in the overlay's hint bar (red for the first, yellow for the rest) — `OverlayScreen` was the only screen not wrapped in a `Scaffold`.** User reported this as a visual bug in the overlay's instructional text (drag/click/Space/Esc hints); it turned out to be unrelated to any of the overlay's own styling. Took an unusually long elimination pass — 15+ real rebuild-and-screenshot cycles — because every plausible cause kept surviving direct tests:

- Not `GlassPanel`'s shadow/blur/border: a completely bare `Text` widget dropped into the same screen showed it too.
- Not any native `NSWindow` property `ShoShotNative.enterOverlay` sets: individually neutralized `level`, `collectionBehavior`, `styleMask` (even swapped `.borderless` for `.titled`), activation (`NSApp.activate`/`makeKeyAndOrderFront` → `orderFrontRegardless` → nothing at all), `isOpaque`/`backgroundColor`/`hasShadow`, and window size (full display → same 960×640 as Home) — one at a time, rebuilding and re-screenshotting each time. None of it moved the artifact.
- Not the frozen-screenshot `RawImage` background layer, not `Focus`/`autofocus`, not the debug automation server's own call path (`flow.start()` is the exact same call a real click or the tray menu makes).
- Not route-transition type: `/overlay` and `/editor` both use the same zero-duration `_instant()` `PageRouteBuilder` in `app.dart`, yet a real, fully-rendered Editor screen (reached via `capture fullScreen`) was screenshotted directly and confirmed 100% clean.
- Not the captured image being held in memory (disposed it early — still happened), not even the `native.enterOverlay()` method-channel call itself (removed the call entirely — still happened, on an otherwise completely untouched native window still sized/positioned like Home).
- The decisive test: reduced `OverlayScreen.build()` to a single bare `Scaffold`-less `Text('MINIMAL DIAGNOSTIC')` — still underlined. Wrapping that exact same minimal widget in a `Scaffold` (nothing else changed) made it vanish immediately.

Root cause: `HomeScreen`, `SettingsScreen`, and `EditorScreen` all build their content inside a `Scaffold`; `OverlayScreen` was the one screen in the app that didn't (it's a raw `Focus`/`Stack` tree, historically because it's a full-bleed custom-painted canvas with no need for Material chrome). Whatever mechanism was producing the underline — most likely some OS/accessibility layer reacting to the absence of `Scaffold`/`Material`'s semantics boundary, never fully identified beyond that — only manifests on screens missing that wrapper. Fix: wrapped `OverlayScreen.build()`'s existing return value in `Scaffold(backgroundColor: Colors.black, body: ...)` (and the early `session == null` fallback too, for consistency) instead of changing anything inside it. Verified visually with the real hint bar, selection handles, and action bar all present and functioning, both before and after making a selection. Lesson for next time this shape of bug shows up (text/rendering artifact tied to *which screen* rather than *what's drawn*): check whether the screen shares the same top-level structural wrapper (`Scaffold`/`Material`) as the working screens before chasing styling or native window properties.

**Added 2026-09-21: Text capture (OCR) — a 4th `CaptureMode`, wired into Home, tray, the overlay's action bar, and the editor.** `CaptureMode.text` behaves exactly like `area` for selection (drag a rectangle; no special-cased hint text, no window-picking) — the only difference is what happens on confirm. Kept deliberately minimal: no new review/edit panel, since the user confirmed the extracted text should just be copied straight to the clipboard with a toast, mirroring the existing "Copy" flow for images.

- **Where it shows up:** Home gets a 4th `_CaptureCard` and the tray gets a 4th menu item *for free* — both already iterated `CaptureMode.values`/`OverlayAction.values` generically before this feature, same for the Settings hotkey list and the debug server's `capture`/`confirm`/`action` commands (matched by `.name`). Only the *exhaustive* switches needed new cases, and Dart's compiler pointed at every one of them the moment the enum value was added: `strings.dart` (`modeName`/`modeDescription`, PT+EN), `home_screen.dart` (`_CaptureCard._icon`, and `FlowMessageKind` in `_showPendingMessage`). Default hotkey `Ctrl+Shift+4` added in `app_settings.dart`.
- **The action itself:** new `OverlayAction.extractText` (added to the enum, not a separate mechanism) — shows as a 5th button in the overlay's action bar (`Icons.text_fields_rounded`, `⌘/Ctrl+T`) for *any* area/window selection, not just text-mode ones; `active: isTextMode` highlights it (and un-highlights Edit) when the capture was started as text mode specifically, and `_confirmDefault()` routes Enter straight to `extractText` in that mode instead of consulting the `afterCaptureAction` setting (which is about images). Editor gets its own `GhostButton` + `⌘/Ctrl+T`, running OCR on the full rendered canvas (`_renderFinal()`, the same helper Copy/Save already used) — deliberately does **not** close the editor afterward (non-destructive, unlike Copy/Save), unlike `completeOverlay()`'s `extractText` case which does finish the flow like every other overlay action.
- **`lib/services/ocr_service.dart`** (new): the actual per-platform dispatch. macOS/Windows go through `NativeBridge.recognizeText(png)` → the `shoshot/native` channel; Linux tries shelling out to `tesseract <file> stdout --psm 6` first (temp file via `path_provider`, same pattern `CaptureService` already uses for the Wayland screenshot fallback), falling through to the native channel only if that's not on `$PATH`. Both `NativeBridge.recognizeText` and the native side's `default:`/`else` branches already returned "not implemented" gracefully (`MissingPluginException` → `null`) before this feature, for other methods — so a platform with no OCR implementation degrades to the `FlowMessageKind.noTextFound` toast, not a crash. `CaptureFlow` never touches the clipboard-image path for this: recognized text goes through Flutter's own `Clipboard.setData(ClipboardData(text: ...))`, not `NativeBridge.setClipboardImage` (that one's PNG/RGBA-specific).
- **macOS (real, tested end-to-end via the debug server):** `ShoShotNative.swift` adds `recognizeText` using `Vision` (`VNRecognizeTextRequest`, `.accurate` + language correction, no `recognitionLanguages` override — Vision reads the user's OS language preferences itself). Verified with `capture text` → `select x y w h` → `confirm extractText` and reading `pbpaste`: recognized real on-screen Portuguese paragraphs correctly, including accents, and correctly excluded text that was only partially inside the selection rect (crops before recognizing, doesn't OCR the whole frozen screenshot). Also verified the editor's button (`action extractText` via debug server) recognizes the full canvas and leaves the editor open, and that a blank-region selection reports "no text found" without touching the clipboard.
- **Windows: deliberately not implemented, on purpose, not just unverified.** `Windows.Media.Ocr.OcrEngine` is WinRT-only — this project's Windows native code (`shoshot_native.cpp`) is plain Win32/COM with no C++/WinRT projection set up, and standing that up is a build-system change (NuGet `Microsoft.Windows.CppWinRT` or hand-rolled COM ABI activation via `RoGetActivationFactory`), not just new code in the existing file. Worse, it's not syntax-checkable through this project's Docker+mingw verification step the way every other Windows addition has been (mingw doesn't ship the WinRT projection headers), so shipping a guess here risked landing something that silently fails to even compile on a real Windows box — worse than not having the feature. Left `recognizeText` unhandled in the `HandleMethodCall` `else if` chain on purpose; it already falls through to the existing `result->NotImplemented()` default, which `OcrService`/`NativeBridge` already treat as "no text found," not an error. Same reasoning applies to `linux/runner/shoshot_native.cc` — no `recognizeText` case needed there either, since the Dart-side `tesseract` fallback runs first and the existing `fl_method_not_implemented_response_new()` default covers the rest. **Refined 2026-09-21: editor's "extract text" moved from a one-shot toolbar button to a proper tool (`ToolType.ocr`) in the left rail.** User feedback after trying the feature: OCR in the editor should let you drag-select the exact region, like every other shape tool, rather than always grabbing the whole canvas from a button. `ToolType.ocr` reuses the *entire* existing drag-to-create-a-shape pipeline in `editor_controller.dart` (`pointerDown`/`pointerMove`/`pointerUp`, the same `_DragKind.draw` path arrow/rect/blur already use) — the only branch point is in `pointerUp`: when `_tool == ToolType.ocr`, the finished `ShapeAnnotation`'s `rect` is handed to a new `onOcrRegion` constructor callback instead of being pushed onto `_annotations`/history, so nothing is left behind on the canvas and Undo has nothing to undo. The drag preview uses a fixed cyan `AnnotationStyle` (`_ocrDraftStyle`) independent of whatever stroke color/width the user currently has selected for real annotations, specifically so a "this is a selection, not a shape you're drawing" distinction is visible while dragging. `EditorScreen` wires `onOcrRegion` to a new `_extractTextInRegion(Rect)`, which renders the full canvas once (`_renderFinal()`, same helper Copy/Save/whole-image-OCR already use) and crops it with a new `ExportService.crop(image, rect)` (mirrors `CaptureSession.crop` from the overlay, but simpler — editor coordinates are already in image-pixel space, no `pixelRatio` conversion needed) before running the same `_recognizeAndCopy` OCR+clipboard+toast helper `_extractText()` (the whole-canvas path) also now shares. The old top-toolbar "Extract text" `GhostButton` was removed — the tool replaces it as the primary/discoverable entry point — but the `⌘/Ctrl+T` shortcut and the whole-canvas `_extractText()` method stay, as a fast path for "just grab everything" that doesn't need switching tools or dragging. Keyboard shortcut for the tool itself: plain `O` (T was already the Text-annotation tool, and ⌘/Ctrl+T means the whole-canvas shortcut). Verified via the debug server (already-generic `tool ocr` + `draw x1 y1 x2 y2` commands, since both are driven by `ToolType.values`/direct `pointerDown`/`pointerMove`/`pointerUp` calls with no per-tool special-casing needed there): confirmed `annotations=0` after the drag (nothing committed), the recognized text in `pbpaste` matched only what was inside the dragged rect, and the editor stayed open afterward.

**Fixed 2026-09-21: adding the 12th tool overflowed `ToolRail` vertically on small editor windows.** `ToolRail` sits in a `Positioned(top: 64, bottom: 84, child: Center(child: ToolRail(...)))` in `editor_screen.dart` — bounded height, but `Column(mainAxisSize: min)` doesn't respect a max height, it just renders past it, producing the classic yellow/black "RenderFlex overflowed" stripe once there isn't room for every icon (visible on a small editor window — e.g. opened from a small area capture, `_editorWindowSize` can clamp down toward `minSize`). Fix in `editor_panels.dart`: wrapped the `Column` in a `SingleChildScrollView`, which — given the same bounded-but-not-fixed height from its parent — sizes to its content when everything fits and scrolls instead of overflowing when it doesn't, with no other layout changes needed. Confirmed via the debug server: reproduced the overflow first (small `_editorWindowSize`, screenshot showed the warning stripe covering the bottom few tools), then confirmed it was gone after the fix and that `tool ocr` still selects the tool correctly even while scrolled out of view. Worth remembering if more tools get added later: this rail has no built-in ceiling on icon count anymore, it just starts scrolling.
