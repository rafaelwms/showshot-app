## What this is

Show Shot — a Flutter desktop screenshot/annotation app for macOS, Windows and Linux (Flameshot/Lightshot-style: freeze the screen, pick an area/window/full display, annotate, copy or save). Lives in the menu bar/tray, responds to global hotkeys. See [README.md](README.md) for the full user-facing feature list and platform build steps — this file is for working *on* the code, not using the app.

**Cross-machine note:** this project gets worked on from multiple machines (macOS, Windows 11, Ubuntu 26.04 x64/arm64). This file is the shared source of truth for status/next-steps across those sessions — keep the "Current status" section below updated as work lands, so a Claude session opened on a different OS picks up where the last one left off instead of re-discovering it.

## Commands

```bash
flutter pub get                          # install deps (run after any pubspec.yaml change)
flutter analyze                          # static analysis — keep this at "No issues found!" before wrapping up
dart format lib                          # format (CI-equivalent: dart format --set-exit-if-changed lib)
flutter run -d macos|windows|linux       # run in debug (starts the debug automation server, see below)
flutter build macos|windows|linux --release
```

There is no automated test suite yet (`test/` is empty — the app is verified via `flutter analyze` plus the debug automation server below). If you add tests, `flutter test` / `flutter test test/some_test.dart` is standard.

### Debug automation server (no mouse/keyboard needed)

Debug builds (`kDebugMode`) open a line-oriented TCP server on `127.0.0.1:47391` (`lib/debug/debug_server.dart`) that drives the whole capture → overlay → editor flow programmatically — essential when you can't simulate real clicks (no Accessibility permission on macOS, and Wayland blocks synthetic input entirely on Linux):

```bash
printf 'capture area\n' | nc 127.0.0.1 47391
printf 'select 100 100 600 400\nconfirm edit\n' | nc 127.0.0.1 47391
printf 'tool arrow\ndraw 50 50 300 200\ntext 100 300 hi\naction save\n' | nc 127.0.0.1 47391
```

Commands: `capture area|window|fullScreen|text [fromHome]` (`fromHome` mimics clicking a Home card), `select x y w h`, `hover x y`, `windows` (lists detected windows), `confirm edit|copy|save|cancel`, `tool <name>`, `draw [shift] x1 y1 x2 y2 [...]`, `text x y <text>`, `typing x y <text>` + `commit` (edit text without confirming, to look at the inline editor), `color AARRGGBB`, `style <width> <opacity> [fill]`, `undo`, `action save|saveAs|copy|extractText|discard`, `setting ask|copyAfterSave|magnifier|jpg|language true|false|<value>`, `smooth 0..1` (pen/marker curve smoothing, also applies to the selection), `notify copied|saved|saveFailed|textCopied|noTextFound` (sends that message as an OS notification and replies `delivered=true|false`), `trayaction area|window|fullScreen|text|openApp|menu` (sets the left-click action; `trayaction click` simulates the left click — avoid `menu`, the native popup blocks the event loop), `editorwindow normal|maximized|fullScreen` (how the editor opens), `winstate` (visible/maximized/fullScreen/size of the OS window), `home`, `banner on|off` (forces Home's screen-recording-permission banner without the OS prompt), `settings`, `hide`, `close`, `stage`, `quit`, plus the inspection helpers `launch` (how the process was started), `visible` (is the window visible to the OS), `dump` (annotations with rotation/bounds/font, selection handles, rotation handle, properties-bar font), `render` (flattens exactly like Copy/Save and writes `~/Pictures/shoshot_debug_render.png` — the only place both the sandboxed app and a shell can reach; delete it afterwards) and `demo` (opens the editor on a generated 3840x2160 image: **works without the screen-recording permission**, which macOS re-asks after every rebuild of the ad-hoc-signed debug app).

Debug-server gotchas learned the hard way: (1) `printf … | nc` half-closes the socket, and the server drops async replies once it sees EOF — commands that `await` something (`visible`, `home`, `capture`, …) look like they hang or print nothing. Use a small client that keeps the socket open until the reply arrives (a 10-line Python `socket` script does it). (2) `action <anything unknown>` falls through to *save*, which pops the Save As panel when "ask where to save" is on — a native modal you can't dismiss without UI automation. (3) `action discard` opens the app's own confirm dialog when there are annotations; use `close` to leave the editor from automation. (4) The app is sandboxed, so a shell can't read its container (`~/Library/Containers/com.rafaelwms.showshot`) — that's why `render` writes to `~/Pictures`.

Hot-reload a running `flutter run` session from another shell with `kill -USR1 <pid>` (find the `dartvm ... flutter_tools.snapshot` process), rather than restarting — the debug server survives reloads.

## Architecture

**One OS window, three roles.** There's a single native window that switches between *home* (Material UI), *overlay* (borderless, frozen-screen selection) and *editor* (annotation canvas) roles — `lib/flow/capture_flow.dart`'s `CaptureFlow` orchestrates the transitions (`window_manager` for resize/show/hide, `Navigator.pushNamedAndRemoveUntil` for the route swap). Routes: `/`, `/settings`, `/overlay`, `/editor`, and a `/blank` route used briefly during transitions specifically to drop widget references to a `ui.Image` *before* it gets disposed (skipping that step throws "Cannot clone a disposed image").

**Native bridge, one per platform, same Dart-side contract.** `lib/services/native_bridge.dart` talks to a `shoshot/native` method channel implemented independently per platform — there is no shared native code:

| Platform | File | Capture | Window list | Overlay |
| --- | --- | --- | --- | --- |
| macOS | `macos/Runner/ShoShotNative.swift` | ScreenCaptureKit (`SCScreenshotManager`, macOS 14+) → `CGDisplayCreateImage` fallback | `CGWindowListCopyWindowInfo` | borderless `NSWindow` at `.screenSaver` level |
| Windows | `windows/runner/shoshot_native.cpp` | GDI `BitBlt` per monitor (per-monitor DPI) | `EnumWindows` + DWM (skips cloaked/tool windows) | `WS_POPUP` + `WS_EX_TOPMOST` sized to the monitor rect |
| Linux | `linux/runner/shoshot_native.cc` | X11 `XGetImage`; Wayland: `org.freedesktop.portal.Screenshot` | `_NET_CLIENT_LIST_STACKING` (X11); Wayland: none — Window mode uses the portal's interactive picker | `gtk_window_fullscreen_on_monitor` |

`DisplayInfo` (`lib/models/display_info.dart`) normalizes the coordinate systems: macOS reports points (`globalIsPhysical: false`), Windows/Linux report physical pixels (`globalIsPhysical: true`) — `NativeBridge.getDisplays()` reads `platformInfo()` once and converts accordingly. Never assume one scale everywhere.

**Capture flow:** `CaptureService.captureUnderCursor()` freezes the display under the *cursor* (not the focused display) into a `CaptureSession` (`lib/models/capture_session.dart`), which holds the raw `ui.Image` plus the window list already translated into that display's local logical coordinates (`CaptureSession._localizeWindows`). The overlay (`lib/ui/overlay/overlay_screen.dart`) never touches native APIs directly — it only reads the frozen `CaptureSession`.

**Overlay hit-testing gotcha (already fixed once, don't reintroduce):** the overlay's full-screen `Listener` (drag-to-select) must **not** be an ancestor of the floating action bar / hint / magnifier. A `Listener` receives every raw pointer event under its subtree regardless of which descendant widget consumed it — so if the action bar is a child, clicking a toolbar button also re-triggers `_onDown` on the Listener and looks like "the selection just expanded". They must be siblings inside the same `Stack` so the Stack's hit-test short-circuits at the topmost hit child. See the `build()` method's structure/comment in `overlay_screen.dart`.

**Window-picker mode vs. area mode** (`CaptureMode.window` vs `.area`) share the same `OverlayScreen`, differentiated by mode checks in the pointer handlers: window mode never builds a free-drag rectangle (any mouse-down+up resolves to whichever window is under the cursor at release, regardless of incidental drag distance — real clicks always have a few pixels of jitter, so gating on "did it move" breaks window-picking). Window mode also swaps the system cursor for a custom camera-icon badge and drops the magnifier/crosshair (`_isWindowPickPhase` in `overlay_screen.dart`), and the hovered window is "spotlighted" (undimmed, like a live selection preview) in `overlay_painter.dart`.

**Editor** (`lib/ui/editor/`): `EditorController` (a `ChangeNotifier`, not a widget) owns the annotation list, undo/redo stack, active tool/style and viewport transform; `EditorCanvasPainter` just renders `controller.paintable`. Annotations (`lib/models/annotation.dart`) are a small sealed-ish hierarchy (`ShapeAnnotation`, `StrokeAnnotation`, `TextAnnotation`, `NumberAnnotation`) each implementing `paintLocal`/`hitTestLocal`/`translated`/`withHandle`/`rotatedBy` (see the rotation model below) — add new tools here, not by branching on `ToolType` elsewhere. Coordinates throughout the editor are *image pixel* space, not logical/window space (`EditorController.pixelRatio` converts UI slider values like stroke width to pixels).

**Services are plain classes wired by hand** in `lib/main.dart` and exposed via `AppScope` (a thin `InheritedWidget`, `lib/core/app_scope.dart`) — there's no DI framework. `SettingsService` and `CaptureFlow` are `ChangeNotifier`s persisted/observed the normal Flutter way; widgets read them via `AppScope.of(context)` + `ListenableBuilder`.

**i18n gotcha:** `Strings.of(context)` (`lib/core/strings.dart`) returns a `const` PT/EN instance — cheap, but that means a screen that captures it *outside* a `ListenableBuilder` reactive to `services.settings` will show stale text after an in-page language change (this happened once in `SettingsScreen` — fixed by moving the whole screen inside one `ListenableBuilder`). Any screen with a live language-dependent control needs the same pattern.

**Windows OCR (`recognizeText`) implemented and verified end-to-end (2026-09-22)** — the one piece that actually needed new code. Previously deliberately unimplemented (see below) because `Windows.Media.Ocr` is WinRT-only and this project had no C++/WinRT projection set up, and that setup wasn't Docker-syntax-checkable (mingw has no WinRT headers). Now done for real, using the machine's own Windows SDK instead of the `Microsoft.Windows.CppWinRT` NuGet package:
- **Projection headers are generated at CMake configure time, not committed.** `windows/runner/CMakeLists.txt` locates the installed SDK's `cppwinrt.exe` and `Windows.winmd` (both ship with the SDK since ~17763; no NuGet needed) and runs `cppwinrt.exe -input <winmd> -output windows/runner/cppwinrt_generated` if that directory doesn't already exist. **Don't try to restrict this with `-include <Namespace>` to save space** — it was tried first (seemed to produce the same ~1358-file/~85MB output either way, so the flag may be version-specific or need different syntax) and, more importantly, a restricted run left `IVectorView<OcrLine>`'s `begin()`/`end()` impl undefined at the point of use (`error C3779: a function returning 'auto' cannot be used before it's defined`) — some cross-namespace impl headers only get emitted for the full closure. Generate the whole thing; it's a one-time ~85MB local cache, gitignored (`windows/.gitignore`: `runner/cppwinrt_generated/`), same idea as the NuGet package's own generated cache.
- **C++/WinRT needs C++20 here, not the project's default C++17.** `apply_standard_settings()` (top-level `windows/CMakeLists.txt`) sets `cxx_std_17` for every target; left alone, `winrt/base.h`'s coroutine support falls back to `<experimental/coroutine>`, which this SDK's STL hard-rejects (`error C2338: ... /await ... deprecated ... REMOVED SOON`). Fixed by calling `target_compile_features(${BINARY_NAME} PUBLIC cxx_std_20)` in `windows/runner/CMakeLists.txt` right after `apply_standard_settings()` — scoped to just the `shoshot` binary, not the shared function (which plugins also use). The implementation itself never uses `co_await`/coroutines at all (see below), this is purely to satisfy `winrt/base.h`'s own header-parsing requirements.
- **Implementation is synchronous-blocking on a detached background thread, not coroutine-based** (`windows/runner/shoshot_native.cpp`, guarded by `#ifdef SHOSHOT_HAS_WINRT_OCR` — set by CMake only when generation succeeded, so a machine without a usable SDK falls back to the pre-existing graceful `NotImplemented` path instead of failing the build). `RecognizeText()` takes ownership of the Flutter `MethodResult` and spawns a `std::thread` that: calls `winrt::init_apartment(multi_threaded)` (each thread needs its own COM apartment), decodes the PNG via `InMemoryRandomAccessStream` + `BitmapDecoder`, converts to `Bgra8`/`Premultiplied` `SoftwareBitmap`, runs `OcrEngine::TryCreateFromUserProfileLanguages()` (falling back to explicit `en-US` if the profile languages have no OCR pack installed), calls `RecognizeAsync(...).get()` (blocking — no coroutines needed since we're already off the platform thread), joins `result.Lines()` with `"\n"` (mirrors macOS's Vision-based joining), and calls `result->Success(...)` directly from that background thread. This is the same async-off-platform-thread pattern macOS uses (`DispatchQueue.global`), just via `std::thread` instead of GCD; Flutter's Windows `MethodResult::Success` is safe to call from a non-platform thread (it just marshals the reply into the engine's messenger).
- **Verified for real via the debug server**, all four call sites: `capture text` → `select` → `confirm extractText` (tray/Home path) recognized real on-screen Portuguese paragraphs correctly, including accented characters (é, não, código) and multi-line text — clipboard held the exact recognized text afterward. **Theming (2026-09-20):** the app now follows the OS light/dark mode (`ThemeMode.system` — Flutter's engine already detects this on every desktop platform, no native code needed) and the OS accent color (native-only signal, no Flutter API for it). Verified end-to-end on macOS: toggled System Settings between light/dark and cycled accent colors (including a dramatic Pink) while the app was running — both update live with zero restart. Architecture:

- `lib/core/theme.dart`: `AppPalette` (a `ThemeExtension`) holds the OS-driven tokens (bg/surface/border/text/accent-gradient) for **widget chrome** (Home, Settings, dialogs, editor/overlay toolbars) — read via `context.palette` (`AppPaletteContext` extension). `AppColors` keeps only what must stay fixed regardless of theme: the annotation color swatches, `danger`/`success`/`warning`, and `violet`/`cyan` — the latter two used *only* by `CustomPainter`-drawn canvas chrome (overlay selection border, spotlight, camera-cursor badge, editor selection handles), which is painted directly over arbitrary screenshot content and needs guaranteed contrast a pastel OS accent couldn't promise. Don't blur this line when adding UI: Material widgets → `context.palette`; `Canvas`/`CustomPainter` code → `AppColors` fixed accents.
  - **Don't trust `ColorScheme.fromSeed(seedColor: accent).primary` to look like `accent`.** Material 3 remaps the seed onto its own tonal palette — in dark mode this produced a pale, desaturated periwinkle (`#ABC7FC`) from a real macOS Blue seed (`#0A84FF`), which reads as visibly "wrong" next to the rest of the OS (found by literally sampling the rendered pixel of a themed `Switch`, not by eyeballing a screenshot). `AppTheme.build()` works around this by generating the tonal scheme normally, then overriding `primary`/`onPrimary`/`primaryContainer`/`secondary` back to the literal accent color — keep doing that for any new accent-driven token; don't reach for `scheme.primary` directly expecting it to match.
- `lib/models/system_theme.dart` + `lib/services/system_theme_service.dart` + `NativeBridge.getSystemAccent()`/`onSystemAccentChanged`: reads the OS accent once at startup (awaited before `runApp`, so there's no fallback-color flash) and stays in sync via a native→Dart push (`systemAccentChanged` on the `shoshot/native` channel).
- Per platform: macOS reads `NSColor.controlAccentColor`, observed live via `DistributedNotificationCenter` (`AppleColorPreferencesChangedNotification`). Windows reads `HKCU\Software\Microsoft\Windows\DWM\AccentColor` (ABGR DWORD), refreshed on `WM_SETTINGCHANGE`/`WM_DWMCOLORIZATIONCOLORCHANGED`. Linux reads `org.freedesktop.portal.Settings` (`org.freedesktop.appearance`/`accent-color`) over D-Bus and subscribes to its `SettingChanged` signal — this is a recent portal addition, so expect it to be unimplemented on some setups; the code already falls back to the fixed violet default when the call fails, which is the expected/silent path there, not a bug.
- Icons live in `artwork/` (SVG + PNG sources, both light/dark variants for the app icon and tray icon) — regenerate `assets/branding/`, `assets/tray/`, `windows/runner/resources/app_icon.ico` from there if the mark changes. The macOS tray icon stays a single `isIconTemplate` asset (OS auto-recolors it); Windows/Linux tray icons don't get OS recoloring, so `TrayService` picks the light/dark-glyph asset itself from `PlatformDispatcher.platformBrightness`.
- **macOS app icon is now an Icon Composer `.icon` bundle** (`macos/Runner/ShowShot.icon`, sourced from `artwork/ShowShot.icon` — regenerate/re-copy from there if the icon changes), not a classic `AppIcon.appiconset` (deleted). Wiring one into this Flutter-template project (classic `objectVersion = 54` pbxproj, not the newer synchronized-groups format) took real trial and error — don't rediscover it:
  - It must be added as a **loose `PBXFileReference`** in the target's Resources build phase (`macos/Runner.xcodeproj/project.pbxproj`), with `lastKnownFileType = com.apple.iconcomposer.icon;` — that exact string is the real system UTI (confirmed via `mdls -name kMDItemContentType` on any `.icon` file), not an Xcode-internal alias like `folder.assetcatalog`. Get this type wrong (e.g. generic `folder`) and the build "succeeds" but just **raw-copies the `.icon` folder into `Contents/Resources/`** instead of compiling it — no error, just a silently wrong result (the app then shows the generic blank-page placeholder icon).
  - It must **not** live inside `Assets.xcassets` in this project — that seemed plausible (works that way in newer, natively-created Xcode 26+ projects using `PBXFileSystemSynchronizedRootGroup`) but silently failed here too (also no icon, also no error) — this template's classic pbxproj apparently needs the explicit loose reference instead.
  - `ASSETCATALOG_COMPILER_APPICON_NAME` (all 3 build configs) must equal the icon's name without extension (`ShowShot`, not `"Show Shot"` — a leftover mismatch from an earlier bulk rename pass, worth double-checking any project-wide find/replace against pbxproj build settings, not just source files).
  - Success looks like: `assetcatalog_output/thinned/ShowShot.icns` appears in the build log, `Info.plist` gets real `CFBundleIconFile`/`CFBundleIconName` values, and nothing named `ShowShot.icon` ends up inside the built `.app`'s `Contents/Resources/`. Verify visually too (`osascript … reveal` + `screencapture`, or just look in Finder) — a wrong-but-non-erroring config is easy to ship unnoticed otherwise.

**Portal identity — `shoshot_register_host_app_id()` in `main.cc`.** Calls `org.freedesktop.host.portal.Registry.Register("com.rafaelwms.showshot")` before anything else (GTK and the Flutter engine both talk to portals during startup; registration must be the connection's first portal call). Without it, an unsandboxed app's portal grants get keyed on whatever the portal infers from the launching process — during development that was *the terminal/Claude*, which silently masked the permission bug below. Grants now live in the permission store under our id and survived a reboot.

**Screenshot portal permission.** GNOME asks once ("Allow Show Shot to take screenshots?"), but **only lets the focused app show that dialog** — journal: `Only the focused app is allowed to show a system access dialog`. The capture flow used to hide our window first, so the very first capture from a hotkey/tray always failed. Now `CaptureFlow.start` checks `hasScreenAccess` (native: `PermissionStore.Lookup("screenshot","screenshot")`) *before* hiding; if missing it shows Home, runs `requestScreenAccess` (a throwaway portal screenshot, which is what triggers the dialog) and continues the capture once allowed. Home's permission banner on Linux has one button, "Permitir capturas", which first deletes a remembered "no" (`DeletePermission`) — otherwise a denial is applied silently forever. **Global shortcuts — `org.freedesktop.portal.GlobalShortcuts`** (`StartBindGlobalShortcuts` native, `HotkeyService` Dart). Wayland apps can't grab keys; they describe shortcuts (id = `CaptureMode.name`, description, *preferred* trigger in XDG format `CTRL+SHIFT+1` — `xdgTrigger()`), GNOME shows "Add Keyboard Shortcuts" once and remembers the approval (later binds return instantly, no dialog). Things learned the hard way:
- **One `BindShortcuts` per session** (`Session already has bound shortcuts`): re-binding closes the session (`org.freedesktop.portal.Session.Close`) and creates a new one.
- Presses arrive as `Activated` with an **`activation_token`** — handed to `gdk_wayland_display_set_startup_notification_id` so the overlay may take focus (verified: physical Ctrl+Shift+1 from another app → overlay focused, Esc works). Tray menu clicks also got focus in testing.
- `trigger_description` comes back as a localized sentence (`Pressione <Shift><Control>1`) → `prettyPortalTrigger()` turns it into `Ctrl+Shift+1`. Both conversions have unit tests (`test/hotkey_format_test.dart`, the first tests in the repo).
- GNOME 50's backend has **no `ConfigureShortcuts`** (interface v1). Settings therefore shows the bound keys read-only plus "Alterar atalhos no sistema" → `gnome-control-center applications com.rafaelwms.showshot` (the page GNOME's own dialog points to; KDE: `systemsettings kcm_keys`). Only re-bind when the shortcut set actually changes (`_portalSignature`) — each bind could pop a dialog.
- `HotkeyService.labelFor(mode)` is what Home/tray/Settings display: on Wayland the user may have picked different keys in GNOME's dialog.

**Window mode on Wayland** has no window list to pick from, so it asks the screenshot portal for an **interactive** capture (GNOME's own screenshot UI, Window tab) and opens the result straight in the editor, like full screen (`CaptureSession.pickedByDesktop`). GNOME reports a dismissed UI as response **2**, not 1 (`InteractiveScreenshot didn't return a file`) — treated as a quiet cancel.

**Wayland clipboard needs focus.** Writes from an unfocused client are dropped *silently*. `completeOverlay` used to hide the overlay and then copy (Copy, Extract text, Save + copy-after-save) — nothing landed. Clipboard work now happens before hiding. The editor copies before closing, so it was fine.

**GTK3/Wayland crashes — all the same signature, `segfault at 40 … in libwayland-client` (`wl_proxy_get_version(NULL)`), found with gdb + apport core dumps (`ulimit -c unlimited`, cores land in `/var/lib/apport/coredump/`) and a debug-server stress loop (`home`/`hide` back to back, plus editor cycles in every window mode):**
1. **`window_manager.hide()` running inside a GTK draw.** `fl_view_renderer_draw` can block in `fl_compositor_render` waiting for a correctly sized frame, and that wait runs Flutter platform tasks — including our `hide` method call — which destroys the wl_surface under the draw in progress (disassembly put the null in `gdk_wayland_window_get_egl_surface`). **Linux hides through native `hideWindow`, which defers `gtk_widget_hide` to a GLib idle callback** (the task-runner wait never iterates the main loop). `CaptureFlow._hideWindow()` — don't call `windowManager.hide()` directly on Linux.

- Belt and braces: `skip_draw_without_surface` in `my_application.cc` drops draws on the window and on FlView's internal `FlViewRenderer` (the widget that actually draws GL) when unmapped or without a wl_surface.

**Fixed 2026-09-20/21: second capture from Home "did nothing" on macOS — two real bugs stacked, plus one wrong fix along the way.** User report: clicking a capture card on the Home window worked once; after returning from the overlay (whether by completing or cancelling with Esc), every further click on Home did nothing at all — but closing the window and reopening it (e.g. from the tray) always unstuck it.

First attempt was wrong and worth recording so it isn't retried: since the debug server's `capture area` (calls `CaptureFlow.start()` directly) reproduced a clean overlay every time, and the only structural difference between "via Home" and "via tray" is whether the click has to land on the app's own window, the working theory was AppKit's standard first-click-suppression on a non-key window. Since the debug server can't drive real clicks, diagnosis from here on used temporary `debugPrint` logging plus having the user reproduce the bug physically while the app ran under `nohup ... > log 2>&1` — the log doesn't need a live `flutter run` session, just redirected stdout, and can be read after the fact without touching the keyboard/mouse. This is the general pattern for this class of bug in this project: the debug server proves the *state machine* logic is correct but can never catch a UI-layer bug, since it doesn't go through real gestures or listener wiring at all.

**Bug 1 (real, but not sufficient on its own): `completeOverlay()`'s `finally` never called `notifyListeners()`.** First log showed `_CaptureCard` rebuilding fine and `MouseRegion.onEnter` firing on every hover (window/hit-testing/mouse-tracking were never broken); the first tap correctly flips `enabled` to `false`; `completeOverlay()` runs its full sequence including `showHome()` (which does its own `notifyListeners()` while `_busy` is still `true`, so Home correctly rebuilds disabled at that point) — but then `completeOverlay()`'s own `finally { _busy = false; }` ran *after* that last notification without calling `notifyListeners()` itself, so nothing told the `ListenableBuilder` that `flow.busy` had gone back to `false`. Fixed by adding `notifyListeners();` right after `_busy = false;` in both `finally` blocks (`start()` and `completeOverlay()`) in `capture_flow.dart`. **This fix was necessary but the bug persisted anyway** — the user re-tested and it was unchanged, which meant there was a second, independent bug.

**Bug 2 (the actual blocker): `const left = _CaptureColumn(); const right = _RecentColumn();` inside the `LayoutBuilder` in `home_screen.dart`.** Re-instrumented with logging directly in `_CaptureColumn.build()` and traced it to Flutter's own `Element.updateChild` optimization: when a parent rebuilds and produces a widget that is `identical()` to the one already mounted in that slot — which `const SomeWidget()` with no constructor arguments always is, since Dart canonicalizes it to a single shared instance — Flutter skips calling `build()` on it entirely (`if (child.widget == newWidget) { ...; return child; }`, no `rebuild()`). `_CaptureColumn`/`_RecentColumn` read mutable state (`AppScope.of(context).flow` etc.) in their own `build()`, so marking their *instantiation site* `const` is exactly the documented Flutter anti-pattern ("don't const a widget that depends on something that can change"). Concretely: a *fresh* route push (e.g. `showHome()` called while `_busy` was still `true`, mid-`completeOverlay()`) mounts a brand-new `_CaptureColumn` element and correctly bakes in `enabled: false` at that moment — but any *later* `notifyListeners()` on the same already-mounted Home (including the Bug 1 fix's own call) tries to update that existing element with the identical `const` instance, and Flutter silently no-ops it. The capture cards were then frozen at whatever `enabled` value happened to be true at last mount, forever, until the next full route push (closing and reopening the window forces exactly that, which is why it "fixed" it). Fixed by dropping `const` from those two instantiations (and the `const Expanded(..., child: right)` that depended on `right` being const) in `home_screen.dart` — plain `final left = _CaptureColumn();` etc.

Lesson for next time this shape of bug shows up (a `ListenableBuilder`/`AnimatedBuilder` that's provably notified but the UI still doesn't reflect new state): check for a `const` widget instantiation *inside* the rebuilding scope that reads inherited/provider state in its own `build()` — `notifyListeners()` firing correctly is necessary but not sufficient if something downstream is `const`-cached. And more generally: a bug that "goes away if you close and reopen the window" is a strong hint that a *fresh mount* is doing something a same-instance *update* isn't — diff those two code paths, don't just add more notifications.

## 2026-09-30 — v1.0.0 day-to-day fixes (after the store launch)

**1. "Launch at startup" opened the Home window instead of staying in the menu bar/tray.** Root cause was per platform:
- **macOS:** a `SMAppService.mainApp.register()` login item carries **no command-line arguments**, so `--autostart` never reaches Dart. The only signal is the launch Apple Event (`kAEOpenApplication` whose `keyAEPropData` is `keyAELaunchedAsLogInItem`). It is readable **only inside `applicationDidFinishLaunching`** — not at nib load, not when AppKit first orders the window in, and `applicationWillFinishLaunching` still sees `currentAppleEvent == nil`. That is too late to simply skip showing the window, and skipping it is not an option anyway: the Flutter macOS engine only starts when the view controller's view is about to appear, so a window that is never ordered in (`visibleAtLaunch="NO"` in the xib was tried) means **Dart never runs** — no tray icon, no hotkeys, nothing. Solution: `MainFlutterWindow.awakeFromNib` starts with `alphaValue = 0` (3 s fail-open in case the event never comes), and `AppDelegate.applicationDidFinishLaunching` calls `MainFlutterWindow.resolveLaunchVisibility()` which `orderOut`s for a silent start or reveals the window otherwise — no flash. `ShoShotNative` exposes it as `launchInfo → {atLogin}`; `NativeBridge.launchInfo()` maps a missing plugin to "not at login". `main()` combines `launch.atLogin || args.contains('--autostart') || args.contains('--hidden')` (CLI args *do* reach Dart on macOS, contrary to an early assumption) and skips `windowManager.show()/focus()` when hidden.
- **A hidden macOS window produces no frames**, so background init (debug server, tray, hotkeys, launch-at-login, Dock icon) now runs inline right after `runApp` instead of in an `addPostFrameCallback` — waiting for a first frame would leave a silently-started app with no tray icon and no shortcuts.
- **Windows:** the runner template shows the window on the first frame unconditionally → `flutter_window.cpp` now skips `SetNextFrameCallback(Show)` when the command line has `--autostart`/`--hidden`. **Linux:** `first_frame_cb` in `my_application.cc` returns early on the same flags. Both were only **syntax-checked in Docker** (mingw-w64 with `-I windows`; GTK3 with `-DAPPLICATION_ID=…`, `-Werror`), never run on real hardware.
- macOS was verified for all four launch modes (normal, `--hidden`, `--autostart`, simulated login item) using a small Swift helper that launches the app with a synthetic `keyAELaunchedAsLogInItem` Apple Event — a real logout/login was not performed. NSLog output from the app did not show up in the unified log; use `/usr/bin/log` (zsh has a builtin `log`) or an in-memory trail if you need to diagnose again.

**2. **4/5. Rotation of every annotation + resizable text with the Select tool.** Model (`lib/models/annotation.dart`):
- Geometry stays in a local, un-rotated frame; `rotation` (clockwise radians) turns it about `pivot` = the centre of the *un-rotated* bounds. That centre does not move when the rotation changes, so repeated rotations can't drift. `paint`/`hitTest` are template methods that rotate the canvas/probe point and call `paintLocal`/`hitTestLocal`.
- **Arrows/lines bake rotation into their endpoints** (rotated about the midpoint) instead of storing an angle; their rotation handle sits sideways from the midpoint. Strokes, text, number badges, rectangles, ellipses and blur store `rotation`. Blur samples the *un-rotated* screenshot through a rotated clip path, so its content is not rotated, only its window.
- `handles` and `rotationHandle(distance)` are returned in **world** coordinates (`rotationHandleScreenDistance = 28 px` on screen; the controller passes `28 / zoom`). Resizing a rotated shape keeps the opposite corner fixed in world space.
- **Text resize scales `style.fontSize`** (clamped 6–1200 px) rather than a box size: the pointer is projected onto the box diagonal in the text's own axes and the opposite corner stays anchored. `EditorController` then syncs `_style` from the resized annotation, otherwise the properties-bar font slider would show — and on touch re-apply — the old size.
- `EditorController` drag kinds are now draw/move/handle/**rotate**; Shift snaps the *resulting* angle to 15° (also uses `_constrain(..., angle:)` for resizing rotated shapes). The canvas paints the selection outline rotated plus a round handle on a stem; `EditorScreen` shows a `grab` cursor over it and wraps the inline text editor in `Transform.rotate` so rotated text is edited rotated.
- Verified via `dump`/`render` on macOS: all six annotation types rotate (handle drags land on the requested angles to 0.1 px), undo restores angle and font size, Shift snapping, hit-testing of rotated shapes (outline hit, empty interior of an unfilled rectangle not hit), resizing rotated text keeps the anchor exactly fixed, and the exported PNG matches the on-screen canvas including rotated blur. A small (~1%) width difference between the inline `TextField` and the committed painter text exists with or without rotation — pre-existing, left alone.

**Changed 2026-09-30: title bar is 56 px (was 44) and its content is vertically centered.** User complaint: the window buttons and the editor's Descartar/Copiar/Salvar hugged the top edge. Two causes: (1) in `WindowTitleBar` the `Row` was a non-positioned child of a `Stack`, so it was only as tall as its content and stuck to the top of the bar regardless of `height` — now wrapped in `Positioned.fill`; (2) on macOS the native close/minimize/zoom buttons stay at AppKit's fixed top spot under `TitleBarStyle.hidden`. `MainFlutterWindow.layoutTrafficLights()` grows the system title-bar container to `titleBarHeight` (56, **keep in sync with `WindowTitleBar.defaultHeight`**) and centers the buttons in it; AppKit resets that on resize/key/full-screen, so it is re-applied from `NSWindow` notifications and after `exitOverlay` (style-mask change). **Added 2026-09-30: pen and marker strokes can be scaled with the Select tool.** `StrokeAnnotation` now has four corner handles (`handles`/`withHandle` in `annotation.dart`) on the box of the *path* (without pen width), rotated with the stroke. `withHandle` scales every point about the opposite corner in the stroke's own axes, then translates so that corner stays exactly where it was on screen (the pivot moves with the new bounds, so this correction is needed — same idea as resizing rotated shapes). The pen width is deliberately not scaled (matches rectangles/ellipses); dragging past the anchor flips the path; a scale factor is clamped to |0.02| so it can't collapse; a perfectly flat path (straight horizontal/vertical stroke) only scales along its non-flat axis. **Shift** keeps proportions via `StrokeAnnotation.proportionalHandleTarget` (pointer projected onto the corner diagonal), wired in `EditorController.pointerMove`'s handle case. Verified with `dump`: anchor fixed and dragged corner lands exactly on the pointer both unrotated and rotated 40°, Shift keeps the aspect ratio (1.3336 -> 1.3334), undo restores, marker and flat strokes behave.

**Added 2026-09-30: curve smoothing for the pen and marker.** `AnnotationStyle.smoothing` (0 = off, the default, to 1) — a slider in the properties bar (`Icons.waves_rounded`, "Smooth curves"/"Suavizar curvas", shown for the pen/marker tools or when a stroke is selected; values snap to 5% steps). It is **non-destructive**: `StrokeAnnotation.points` stays the raw pointer path and `renderPoints` (cached per instance in an `Expando`) runs it through `smoothPath` — resample to an even ~3 px spacing, Gaussian convolution with sigma = 2 + 38·level image-pixels, ends extended by point reflection so the first/last point stay put and straight runs stay straight. Bounds, handles, hit testing and painting all use `renderPoints` so they match what is drawn; changing the level on an already-drawn stroke re-smooths it (and is undoable, like any style change). Because smoothing shaves corners, `withHandle` (corner resize) nudges its scale factors up to 3 times so the *drawn* box lands exactly on the pointer and re-anchors on the drawn opposite corner — verified to 0.0 px on three corners. Tuning note: with real (dense) mouse input 25% removes pixel jitter, 50% removes hand tremor, 100% is a strong curve; sparse synthetic points (25 px apart) hide the effect.

**Added 2026-09-30: outcome messages ("Copied", "Saved to…", "Text copied", "No text found", "Could not save") are now OS notifications.** Before, they were snackbars — and after Copy/Save the editor closes and the window hides, so nobody saw them. `NotificationService` (`lib/services/notification_service.dart`) maps a `FlowMessage` (now in `lib/models/flow_message.dart`, re-exported by `capture_flow.dart`) to text (`NotificationService.textFor`, shared with the in-app toasts) and calls `NativeBridge.notify(title, body)` → `bool` (true only if the OS accepted it; 4 s timeout so a pending permission prompt can't hang a flow). Flow: `CaptureFlow._report(message)` notifies and only falls back to `lastMessage` (Home's toast) when it wasn't delivered; the editor uses `_announce(message)` (notification, else its own toast) and passes `closeEditor(message: null)` when already delivered. `captureFailed` stays in-app on purpose (it brings Home up, which has somewhere to show it). New setting `AppSettings.systemNotifications` (default on; Settings → Save section) — off, or any refusal, falls back to toasts.
- **macOS:** `notify` in `ShoShotNative.swift` uses `UNUserNotificationCenter`; asks for permission on the first notification (`.alert` only, no sound) and replies true only when delivered. It **needs the `UNUserNotificationCenterDelegate.willPresent` extension** at the bottom of the file: without a delegate macOS hides notifications while the app is active, which is exactly the editor/Home case. The permission prompt appears as a banner in the top-right ("Notificações de Show Shot") — it can't be answered from automation; the user has to click Allow. No entitlement needed under the sandbox.
- **Windows** (unrun, syntax-checked with mingw): `ShowNotification` adds a temporary second `Shell_NotifyIconW` icon (the app's own) with an `NIF_INFO` balloon (`NIIF_USER | NIIF_NOSOUND`) and removes it with a `SetTimer` callback after 8 s — the real tray icon belongs to the tray plugin, so the balloon can't hang off it. Expect the app icon to flash in the tray for those seconds; if that's ugly on real hardware, the alternative is WinRT toasts (needs C++/WinRT, see the OCR note).
- **Linux** (verified 2026-10-01 with `dbus-monitor`): `org.freedesktop.Notifications.Notify` over the existing session-bus connection, answered asynchronously from the D-Bus reply (`OnNotifyDone`); the app name/icon resolve through the installed `.desktop` file.
